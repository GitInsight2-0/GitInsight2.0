# G1 음성 제공사 비교

같은 대본, 같은 대본 두뇌(LAB_ENABLED), 같은 측정 방식으로 OpenAI Realtime과 Gemini Live를 비교합니다.
측정 이벤트는 `/api/metrics`로 들어가 `.data/metrics.jsonl`에 쌓이고, 화면의 "결과 JSON 복사"로 요약을 받습니다.

## 실행

```text
# 터미널 1: API 서버 (대본 두뇌 켬)
# --reload-dir로 감시 범위를 서버 코드로 좁힙니다.
# 레포 전체를 감시하면 Next 개발 서버가 web/.next에 쓸 때마다 재시작되어 메모리의 세션이 사라집니다 (404 세션을 찾을 수 없습니다).
LAB_ENABLED=true uv run uvicorn --factory gitinsight_api.main:app_factory --reload --reload-dir api/src --reload-dir contracts/src

# 터미널 2: 웹
cp web/.env.example web/.env.local   # LAB_ENABLED=true, 제공사 키 입력
pnpm --filter @gitinsight/web dev    # http://localhost:3000/lab/voice
```

- macOS에서는 레포를 iCloud 동기화 폴더(데스크탑, 문서) 밖에 둡니다. 예: `~/dev/GitInsight2.0`.
  iCloud가 `.venv`의 `.pth` 파일에 숨김 표시를 붙이면 Python이 그 파일을 건너뛰어 `ModuleNotFoundError: No module named 'gitinsight_api'`가 납니다.
  `ls -lO .venv/lib/python3.12/site-packages/*.pth`에 `hidden`이 보이면 이 경우입니다.
- 이어폰을 낍니다. 스피커로 들으면 AI 목소리가 마이크로 들어가 지연과 끼어들기가 잘못 잡힙니다.
- "판단 지연 흉내"는 `?lab_delay_ms`로 서버에 전달됩니다. 판단 LLM 지연 측정(`docs/evals/latency.md`)의 중앙값을 넣어 실제 체감에 가깝게 맞춥니다.
- **지금까지 쓴 800ms는 가정값입니다.** `docs/evals/latency.md`가 아직 비어 있어 근거가 없습니다. 판단 LLM 지연을 재면 그 중앙값으로 다시 잽니다.

## 측정 방식

| 값 | 재는 방법 | metrics 이벤트 |
|---|---|---|
| 응답 지연 | 마이크 소리가 0.5초 멈춘 시각 → AI 출력 소리가 처음 커진 시각. 위임 왕복 포함 | `vad_end`, `first_audio`(value_ms) |
| 위임 왕복 | 도구 호출을 받은 시각 → `/turns` 응답을 도구 결과로 돌려준 시각 | `delegation_start`, `delegation_end`(value_ms) |
| 끼어들기 | AI가 말하는 중에 마이크 소리가 커진 시각부터, AI 출력이 0.15초 이상 조용해지기 시작한 시각까지. 5초 안에 안 멈추면 "안 멈춤". 화면에 "500ms 안에 멈춤 n/전체"로 표시 | `barge_in`(`at_ms`=끼어들기 시작, `value_ms`=멈추기까지) |
| 받아쓰기 vs 도구 인자 | 같은 턴의 받아쓰기(ASR)와 음성 AI가 도구 인자로 준 transcript를 글자 단위로 비교 (0~1). 서버에는 받아쓰기를 보내고, 받아쓰기가 없을 때만 도구 인자를 보냄 | 화면과 결과 JSON에만 (원문은 서버로 보내지 않음) |

제공사 이벤트가 아니라 실제 소리 크기로 재서 두 제공사를 같은 기준으로 비교합니다.

- `scenario`는 대본 줄 번호입니다 (`g1_s1`~). 서버로 턴을 보낼 때마다 다음 줄로 넘어갑니다.
- 분위수(p90, p95)는 선형 보간입니다. 표본이 10개 안팎이면 p90·p95가 최댓값에 가까우니 n을 함께 봅니다.
- 2026-11-11 측정은 위 방식으로 바꾸기 전 빌드라서, 끼어들기 멈춤 시간과 대본 줄별 구분이 없습니다.

## 선정 규칙 (안, 테스트 전에 팀 합의)

| 기준 | 가중치 | 통과 조건 (예시) |
|---|---|---|
| 한국어·코드 용어 인식 | 30% | 대본 핵심 용어(트리시터, FastAPI, useEffect, useReducer) 오인식 1개 이하 |
| 응답 지연 | 25% | 중앙값 1.5초 이하 (판단 지연 흉내 포함) |
| 위임 안정성 | 20% | 10번 중 10번 도구 호출, 질문을 스스로 지어내지 않음 |
| 끼어들기 | 15% | 끊으면 0.5초 안에 AI가 멈춤 |
| 비용 | 10% | 면접 50회 예산 안 |

- 위임에서 실패하면 다른 점수와 상관없이 탈락합니다 (설계 원칙 1: 음성과 판단 분리).
- 점수 차이가 10% 안이면 구현이 쉬운 쪽을 고릅니다.

## 관찰

- Gemini 1·3회차: 답변 중간에 1~2초 멈추면 AI가 답변이 끝난 것으로 보고 말을 시작합니다. 3회차(2초씩 멈추며 말하기)에서 직접 확인했습니다 (제공사 기본값, 민감도 HIGH). 면접 답변은 생각하며 멈추는 일이 많아서, 말 끝 판정(침묵 길이·민감도) 설정을 비교 항목에 넣습니다.
- Gemini 1회차: 지시문에 "다시 말해 달라는 요청도 도구로 넘긴다"고 적었지만 직접 처리했습니다. 반복 판단(REPEAT)을 서버가 하려면 지시문을 더 강하게 하거나, 웹이 받아쓰기를 보고 직접 /turns를 부르는 방식을 검토합니다.
- 응답 지연은 3회 모두 약 3.1초로 일정합니다. 위임 왕복 0.82초(흉내 0.8초 포함)를 빼면 약 2.3초가 Gemini 쪽 시간(말 끝 판정, 도구 호출 결정, 음성 생성)입니다.
- 받아쓰기와 도구 인자의 유사도 최저 0.63~0.66: 모델이 도구 인자에 답변을 다듬거나 줄여 넣는 턴이 있습니다. 서버에는 받아쓰기를 보내야 합니다.

## 말 끝 판정 설정 비교 (#26)

Gemini `realtimeInputConfig.automaticActivityDetection`의 `silenceDurationMs`, `endOfSpeechSensitivity`를 바꿔 가며 같은 대본을 2초씩 멈추며 말합니다.
테스트 화면의 "말 끝 침묵", "말 끝 민감도"로 바꿉니다. 결과 JSON에 설정값이 함께 남습니다.

| 침묵 (ms) | 민감도 | 응답 지연 중앙값 (ms) | 멈춤에서 끼어듦 | 위임 누락 | 메모 |
|---|---|---|---|---|---|
| 기본값 | 기본값(HIGH) | 3091 | 2회 (3회차) | 미측정 | G1 3회차. 위임 5회 |
| 2000 | LOW | 4111 (p90 4229) | **0회** (귀로 확인) | 0 | 위임 6회 ("질문 다시"도 서버로 넘어감). 끼어들기 감지 1회 |
| 1500 | LOW | 1200 (p90 4409) | | 0 | **위임 8회: 2초 멈춤마다 답변이 쪼개져 서버로 넘어감.** 지연 중앙값이 낮은 건 쪼개진 턴 때문 |
| 3000 | LOW | 5460 (p90 6270) | | 0 | 위임 5회. 끼어들기 감지 4회 (오래 조용하다가 사용자와 AI가 동시에 말을 시작한 것으로 보임) |

측정: 2026-11-11 18:17~18:23 KST, macOS Chrome, 이어폰, 판단 지연 흉내 800ms, 대본을 2초씩 멈추며 말하기, 설정마다 1회.

- 설정은 실제로 적용됩니다. 침묵 2000→3000ms에서 지연이 4.1→5.5초로 늘었습니다.
- 지시문 보강(#26) 뒤 위임 누락은 세 설정 모두 0회입니다. 보강 전에는 3회 중 2회 빠졌습니다.
- 받아쓰기와 도구 인자 유사도 최저가 0.46~0.56까지 내려갔습니다. 모델이 도구 인자에 답변을 다듬어 넣는 경우가 계속 있어, 받아쓰기를 서버로 보내는 방식이 필요합니다.
- 잠정 기본값: **침묵 2000ms, 민감도 LOW**. 남은 과제는 응답 지연 약 4.1초입니다.

- 위임 누락: 사용자가 말한 뒤 도구 호출 없이 AI가 끝까지 말한 턴. 화면과 결과 JSON, `/api/metrics`의 `error`(`delegation_missed`)로 셉니다.
- 같은 모델에서 이 설정이 적용되지 않는다는 보고가 있어 (google-gemini/cookbook#1262), 값만 바꾸지 않고 측정으로 확인합니다.

## 맞장구 비교 (#28)

말 끝 설정은 침묵 2000ms, 민감도 LOW로 고정하고, 테스트 화면의 "AI 맞장구"를 켜고 끄며 같은 대본을 말합니다.

| 맞장구 | 말 끝 → 맞장구 중앙값 (ms) | 말 끝 → 질문 중앙값 (ms) | 위임 누락 | 멈춤에서 끼어듦 | 메모 |
|---|---|---|---|---|---|
| 끔 | - | 약 4110 (측정 버그로 맞장구 칸에 4회 잡힘, 아래 참고) | **0** | | 위임 6회 |
| 켬 | 2789 (p90 3059, 6회) | 4381 (p90 4498, 3회) | **2** | | 위임 3회. "네." 다음에 도구 없이 직접 답한 턴이 생김 |

측정: 2026-11-11 18:31~18:34 KST, macOS Chrome, 이어폰, 판단 지연 흉내 800ms, 대본을 2초씩 멈추며 말하기, 설정마다 1회.

- 맞장구를 켜면 첫 반응이 약 1.3초 빨라지지만(4.1 → 2.8초), 위임 누락이 0 → 2회로 늘었습니다. "음성 AI는 대화만" 원칙이 깨지므로 **모델에게 맞장구를 시키는 방식은 쓰지 않습니다.** 기본값을 끔으로 바꿨습니다.
- 맞장구 켬 회차의 "맞장구" 값에는 모델이 직접 답한 턴의 첫소리도 섞여 있습니다.
- 측정 버그: 도구 결과를 보낸 뒤 AI가 말하기 전에 마이크에 작은 소리가 잡히면, 질문 첫소리가 맞장구로 잡혔습니다. 끔 회차의 맞장구 칸 4회(중앙값 4110ms)는 실제로는 질문 첫소리입니다. 질문 측정 상태를 따로 두도록 고쳤습니다.
- 다음 후보: 모델 대신 **웹이 같은 목소리로 미리 만든 짧은 "네." 음성을 도구 호출 시점에 재생**합니다. 지시문을 바꾸지 않아 위임 누락이 늘지 않습니다.

- 말 끝 → 맞장구: 도구 결과를 보내기 전에 난 AI 첫소리 (`filler_start`).
- 말 끝 → 질문: 도구 결과를 보낸 뒤 난 AI 첫소리 (`first_audio`). #28 전의 "응답 지연"과 같은 값입니다.
- 맞장구와 질문 사이 소리가 0.4초 안 끊기면 한 발화로 잡혀 질문 시간이 빠집니다. 위임 왕복이 0.8초 이상이면 생기지 않습니다.

  - 무료 등급으로 개발과 측정을 할 수 있습니다.
  - OpenAI Realtime은 측정하지 않았습니다. 같은 조건의 비교 결과는 없고, 비교 없이 Gemini 단독으로 정했습니다.
- 이유 (회의에서 나온 것): <!-- 회의 기록이 있으면 채웁니다 -->
- 남은 과제 (G4 전에 해결):
  - 응답 지연: 기본 설정 약 3.1초, 멈춤에 강한 설정(2000ms, LOW) 약 4.1초 → 목표 1.5초. 위임 대기 중 짧은 맞장구(계약의 `filler_start`)를 검토합니다.
