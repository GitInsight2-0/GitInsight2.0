# 데모 장애 대응 런북

> 해커톤(11/20~21) 데모 중 외부 서비스가 막혔을 때 이 문서대로 전환합니다.
> "상태" 열이 `준비됨`이 아닌 항목은 아직 쓸 수 없습니다. 담당자가 구현하면 상태를 고칩니다.
> 마지막 갱신: 2026-11-17 (B)

## 판단 기준

- 데모 흐름(4분): 로그인·레포 선택·동의 → 캐시된 분석 결과 → 음성 면접 → 하이라이트·변경 이력 → 리포트·코드 지도·이전 비교
- 한 단계에서 **10초 넘게 반응이 없으면** 다음 대비책으로 넘어갑니다. 원인을 그 자리에서 고치지 않습니다.
- 전환은 발표자가 아닌 시연 보조가 맡습니다. 발표자는 "대비 경로로 이어 가겠습니다" 한 문장만 말합니다.

## 전환 방법

환경 변수는 Railway API 서비스의 Variables에서 바꾸고 재배포합니다. 재배포는 약 1~2분 걸리므로, 기다리는 동안 텍스트 모드로 이어 갑니다.

### A. 판단·리포트 LLM 모델 바꾸기

판단·분석·리포트 LLM은 Gemini만 씁니다 (`LLM_PROVIDER` 기본값 `gemini`, #63). 다른 제공사로 넘기는 대비책은 없습니다.
기본 모델은 판단 `gemini/gemini-3.6-flash`(추론량 `low`, 제한 4초), 분석·리포트 `gemini/gemini-3.8-flash`입니다.
한 모델이 과부하(503)나 한도 초과(429)로 막히면 같은 키로 다른 Gemini 모델을 씁니다.

```text
LLM_JUDGE_MODEL=gemini/gemini-3.8-flash     # 판단 모델이 막혔을 때
LLM_REPORT_MODEL=gemini/gemini-3.6-flash    # 리포트 모델이 막혔을 때
```

- 되돌릴 때는 변수를 비웁니다. 비우면 기본 모델을 씁니다.
- 바꾸기 전에 로컬에서 확인합니다: `$env:LLM_JUDGE_MODEL="gemini/gemini-3.8-flash"; uv run python scripts/demo_check.py --real-llm`
- 판단을 3.8 Flash로 바꾸면 느려집니다 (추론량 `low`에서 중앙값 3.8초, 제한 4초에 거의 닿음). 대체 사유 `timeout`이 많으면 B로 갑니다.
- 키 자체가 막혔거나(인증 오류, 결제 한도) Gemini 전체 장애면 모델을 바꿔도 소용없습니다. 바로 B로 갑니다.
- 무료 등급 키로는 판단 호출이 거의 다 실패했습니다 (429, 503). 배포에는 결제를 등록한 키를 넣습니다.
- 지연 측정 기록은 `docs/evals/latency.md`에 있습니다 (2026-11-17, 모델과 추론량별 10회).

### B. LLM 없이 진행

```text
BRAIN_FORCE_PREPARED=true
```

- 면접 계획, 답변 판단, 리포트에서 LLM을 부르지 않습니다.
- 질문은 주제별 기본 질문과 미리 만든 꼬리질문 2개로 나가고, 리포트는 턴별 판단 표로 나옵니다.
- 로컬 확인: `$env:BRAIN_FORCE_PREPARED="true"; uv run python scripts/demo_check.py`

### C. 텍스트 모드

- 면접 화면의 모드 전환으로 텍스트 입력으로 바꿉니다. 음성과 같은 면접 두뇌 API를 씁니다.
- [미구현] 화면 전환 버튼은 C의 T8에서 만듭니다.

## 데모 전 점검 (당일 아침, 리허설 전)

```text
uv run python scripts/demo_check.py               # LLM 없이 완주
uv run python scripts/demo_check.py --block-llm   # 판단 LLM 오류 상황에서 완주
uv run python scripts/demo_check.py --real-llm    # 실제 LLM으로 완주 (비용 발생)
```

세 명령 모두 마지막 줄까지 `[통과]`여야 합니다. `--real-llm`에서 대체 사유가 `timeout`으로 많이 나오면 `JUDGE_TIMEOUT_S`나 `LLM_JUDGE_REASONING_EFFORT`를 조정합니다.
리포트가 판단 표(`turn_table`)로 자주 나오면 리포트 생성이 제한 30초(`REPORT_TIMEOUT_S`)를 넘는 것입니다. 리포트 모델의 추론량은 `LLM_REPORT_REASONING_EFFORT`(기본 `low`, 12초 안팎)로 바꿉니다. 비우면 모델 기본값(23~28초)을 씁니다.

- [ ] Railway 환경 변수: `LAB_ENABLED=false`, `BRAIN_FORCE_PREPARED=false`, `LLM_PROVIDER`와 모델 이름 변수 비움 (기본값 Gemini)
- [ ] Railway 시작 명령이 `uvicorn --factory gitinsight_worker.server:app_factory`인지 확인 (`gitinsight_api.main:app_factory`이면 분석 요청이 503)
- [ ] `GEMINI_API_KEY`를 Railway(판단·분석·리포트)와 Vercel(음성 토큰)에 등록, 결제 한도 확인 (예산 상한 $100)
- [ ] 데모 레포 분석 스냅샷을 운영 DB에 넣고(`seed_demo_analysis.py --user-id <데모 계정 id> --fixture gitinsight_agent_live --analysis-id demo-gitinsight-agent`), `demo_check.py --from-db --user-id <데모 계정 id>`로 확인 (A)
  - `--analysis-id demo-gitinsight-agent`는 웹 첫 화면의 "데모 레포로 바로 시작"(`web/lib/demo.ts`)과 같은 id입니다. 빼면 이 버튼이 404입니다
  - `--user-id`는 데모에 로그인할 계정의 GitHub 숫자 id입니다 (`gh api users/<login> -q .id`). 로그인 이름이 아닙니다
  - 서버는 `DATABASE_URL`이 있으면 DB의 분석만 쓰고 요청한 본인에게만 열어 줍니다. `--user-id`가 다르면 세션 시작이 404입니다 (#52)
  - `demo_check.py --from-db`도 서버와 같은 소유자 확인을 거칩니다. 스냅샷을 넣은 `--user-id`와 다르면 실패로 끝납니다
  - `gitinsight_agent_live`는 레포 주인(D)이 요청했다고 보고 실제 워커로 만든 결과라 기여 라벨이 모두 본인 기여입니다. 다른 계정으로 시연하면 `eval_stage2.py --requester-email ... --save-json`으로 다시 만듭니다
- [ ] 녹화 영상을 발표 노트북에 내려받아 둠 (C)
- [ ] 모바일 핫스팟 연결 확인
- [ ] 시연 계정의 마지막 리허설 리포트에서 코드 지도의 "막힘" 함수를 확인함. 시연은 그 함수부터 묻습니다 (아래 "같은 계정으로 다시 면접할 때")

## 같은 계정으로 다시 면접할 때

시연 계정으로 리허설을 하면 실제 시연은 재면접으로 시작합니다 (#107).
리포트는 계정별로 쌓이고, 같은 계정이 같은 레포로 다시 면접을 보면 서버가 지난 리포트의 코드 지도를 읽어 질문 순서를 바꾸기 때문입니다.

달라지는 것은 아래와 같습니다.

- 질문 순서: 지난 면접에서 막혔던 함수의 주제, 지난 면접 뒤에 커밋이 들어온 함수의 주제, 나머지 순서로 묻습니다.
- 첫 인사: 첫 주제가 막혔던 함수이면 "안녕하세요, 지난 면접에서 설명하지 못했던 코드부터 다시 여쭤보겠습니다."로 시작합니다. 커밋이 들어온 함수이면 "안녕하세요, 지난 면접 뒤에 커밋이 들어온 코드부터 여쭤보겠습니다."입니다.
- 지난 면접에서 막힌 함수가 없고 새 커밋도 없으면 순서와 인사는 첫 면접과 같습니다.
- 리포트의 "이전 면접과 비교"는 같은 계정의 지난 리포트가 있어야 나옵니다. 그래서 데모 흐름의 이전 비교를 보여 주려면 시연 계정으로 면접을 한 번은 끝내 둬야 합니다.

시연의 첫 질문은 마지막 리허설로 정합니다.

- 시연에서 처음 묻게 하고 싶은 함수의 질문에, 마지막 리허설에서 "모르겠습니다"로 답합니다. 면접관이 힌트를 줘도 다시 설명하지 않고 다음으로 넘어가거나 면접을 끝냅니다. 그 함수가 "막힘"으로 남아 시연의 첫 질문이 됩니다. 힌트를 받고 설명하면 "힌트 받고 설명함"이 되어 다시 묻지 않습니다.
- 함수마다 가장 최근 면접의 상태로 봅니다. 앞선 리허설에서 막혔어도 마지막 리허설에서 설명했으면 다시 묻지 않습니다.
- 막힘은 그 함수에 대한 마지막 답이 "모르겠다"이거나, 주제의 주 코드인데 기대한 요점을 하나도 다루지 못한 경우입니다.
- 리허설 뒤에는 시연용 레포에 커밋을 올리지 않습니다. 커밋이 바뀌면 새로 분석하고, 커밋이 들어온 함수의 주제가 앞으로 옵니다.

첫 면접처럼 시작하려면 그 레포로 면접을 본 적 없는 계정으로 로그인합니다.
이때는 이전 면접 비교가 나오지 않고, 분석은 요청한 본인에게만 열리므로 그 계정으로 레포를 미리 분석해 둬야 합니다.

발표할 때 코드 지도의 숫자를 아래처럼 읽습니다.

- 위쪽 숫자("핵심 함수 N개 중 M개를 설명했어요")는 그 계정이 이 레포로 본 면접을 모두 합친 값입니다. 리허설 결과도 들어갑니다.
- 아래 목록("이번 면접에서 질문받은 함수")만 이번 면접의 결과입니다.
