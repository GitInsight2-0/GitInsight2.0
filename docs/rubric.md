# 평가 루브릭 초안 (팀 검토용)

> 상태: 초안. T10 전에 팀 검토를 받아 확정합니다.
> 리포트 생성(Task 13) 프롬프트가 이 문서의 기준을 그대로 씁니다.

## 원칙

- 점수는 **답변 내용만으로** 매깁니다. git 기여 라벨(`기여 근거 확인`, `공동 기여`, `확인 불가`)은 점수에 쓰지 않습니다.
- 역량마다 1~4점 행동 기준(BARS)을 씁니다. 점수에는 근거가 된 답변 인용문과 `turn_id`가 있어야 합니다.
- 인용문이 실제 자막에 없거나 `turn_id`가 없으면 그 점수는 버립니다.
- 근거가 될 답변이 없는 역량은 점수를 매기지 않습니다. "근거 부족"은 낮은 점수가 아닙니다.
- 이 문서는 국내 기업의 공개 평가 기준을 참고하지 못했습니다(인수인계서 6장).

## 역량별 기준

### 1. 코드 이해도 (`code_understanding`)

| 점수 | 행동 기준 |
|---|---|
| 1 | 함수가 하는 일을 설명하지 못하거나 코드와 다른 동작을 말합니다. |
| 2 | 함수의 큰 역할은 말하지만 입력, 출력, 분기 같은 흐름이 빠지거나 일부 틀립니다. |
| 3 | 주요 흐름과 분기를 코드와 맞게 설명합니다. |
| 4 | 흐름에 더해 경계 상황(예외, 빈 입력, 캐시 미스)과 그때의 동작까지 정확히 설명합니다. |

### 2. 설계 판단 (`design_judgment`)

| 점수 | 행동 기준 |
|---|---|
| 1 | 왜 이렇게 만들었는지 말하지 못합니다. |
| 2 | 선택한 방식은 말하지만 다른 방법과 비교하지 못합니다. |
| 3 | 대안 하나 이상과 비교해 선택 이유를 말합니다. |
| 4 | 대안과의 트레이드오프(성능, 유지보수, 비용)를 구체적으로 말하고, 지금 다시 한다면 무엇을 바꿀지 근거와 함께 말합니다. |

### 3. 문제 해결·장애 대응 (`problem_solving`)

| 점수 | 행동 기준 |
|---|---|
| 1 | 실패 상황을 떠올리지 못합니다. |
| 2 | 실패 상황은 말하지만 원인 추적이나 대응 방법이 막연합니다. |
| 3 | 실패 원인을 찾는 순서와 대응 방법을 구체적으로 말합니다. |
| 4 | 대응에 더해 재발 방지(테스트, 모니터링, 제한 시간, 대비책)까지 말합니다. |

### 4. 확장성·운영 (`scalability_operations`)

| 점수 | 행동 기준 |
|---|---|
| 1 | 트래픽이나 데이터가 늘었을 때의 영향을 말하지 못합니다. |
| 2 | 병목 후보는 말하지만 근거나 해결 방법이 없습니다. |
| 3 | 병목을 근거와 함께 짚고 해결 방법을 하나 이상 말합니다. |
| 4 | 해결 방법의 비용과 측정 방법(지표, 부하 테스트)까지 말합니다. |

### 5. 커뮤니케이션 (`communication`)

| 점수 | 행동 기준 |
|---|---|
| 1 | 질문과 관계없는 답을 하거나 요점을 알기 어렵습니다. |
| 2 | 질문에 답하지만 순서가 뒤섞이거나 용어를 부정확하게 씁니다. |
| 3 | 결론을 먼저 말하고 근거를 순서대로 설명합니다. |
| 4 | 결론과 근거가 분명하고, 상대 수준에 맞춰 예시나 비유로 설명합니다. |

### 6. 역할·의사결정 설명 (`role_decision`)

답변에서 지원자가 직접 말한 내용만 봅니다. git 이력과 대조하지 않습니다.

| 점수 | 행동 기준 |
|---|---|
| 1 | 자신이 맡은 부분과 결정에 대해 말하지 못합니다. |
| 2 | 맡은 부분은 말하지만 무엇을 결정했는지 막연합니다. |
| 3 | 맡은 부분과 내린 결정, 그 이유를 구체적으로 말합니다. |
| 4 | 결정 과정에서 고려한 제약과 팀원과의 조율, 결과를 구체적으로 말합니다. |

## 검토할 것

- [ ] 역량 6개의 이름과 범위가 겹치지 않는지 (특히 설계 판단 ↔ 확장성·운영)
- [ ] 10분 면접(주제 5개)에서 6개 역량 모두 근거가 나올 수 있는지
- [ ] 2점과 3점의 경계 문장이 판단 가능한지
